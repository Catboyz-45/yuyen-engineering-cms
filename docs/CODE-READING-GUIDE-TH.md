# วิธีอ่านโค้ดโปรเจกต์นี้สำหรับผู้เริ่มต้น

## เริ่มอ่านจากที่ไหน

แนะนำให้อ่านตามลำดับนี้:

1. อ่าน [PROJECT-GUIDE-TH.md](./PROJECT-GUIDE-TH.md) เพื่อเห็นภาพรวม
2. เปิดหน้าใน `src/app` ที่สนใจ เช่น `src/app/(public)/products/page.tsx`
3. ดู import ด้านบนเพื่อรู้ว่าหน้านั้นนำชิ้นส่วนและข้อมูลมาจากไฟล์ใด
4. ตามไปที่ service ใน `src/server/services` หรือ `src/server/cms`
5. ตามต่อไป repository ใน `src/server/repositories` เพื่อดูว่าคุยกับตารางใด
6. เปิด `prisma/schema.prisma` เพื่อดูความหมายของช่องและความสัมพันธ์
7. เปิดไฟล์ชื่อใกล้กันใน `tests` เพื่อดูตัวอย่างพฤติกรรมที่ระบบต้องรักษา

## รูปแบบคอมเมนต์ที่เพิ่มไว้

ไฟล์โค้ดที่ทีมเขียนเองมีคำอธิบายภาษาไทยด้านบนในรูปแบบ:

```ts
/**
 * หน้าที่ของไฟล์นี้: ...
 */
```

ฟังก์ชันที่เป็นทางเข้าของโมดูลมีคอมเมนต์ติดอยู่ด้านบน เช่น:

```ts
/** อ่าน session ปัจจุบันและไม่คืน token ดิบให้ผู้เรียก */
export async function currentSession() { ... }
```

คอมเมนต์อธิบาย “เหตุผลและผลกระทบ” ไม่ได้แปลไวยากรณ์ทุกคำ เพราะข้อความแบบ “บวกหนึ่งให้ตัวแปร” จะซ้ำกับโค้ดและเก่าเร็ว สิ่งที่ควรสนใจคือกฎสิทธิ์ กฎข้อมูล จุดเปลี่ยนสถานะ transaction และการจัดการข้อผิดพลาด

## สัญลักษณ์ที่พบบ่อย

| โค้ด | อ่านแบบภาษาคน |
|---|---|
| `const` | ตั้งชื่อให้ค่าที่จะไม่ถูกชี้ไปค่าใหม่ |
| `async` / `await` | งานนี้ต้องรอ เช่น รอฐานข้อมูลหรือ S3 |
| `if (...) return` | ถ้าไม่ผ่านเงื่อนไข ให้หยุดทันที |
| `?.` | ถ้าค่าก่อนหน้าไม่มี ไม่ต้องพยายามอ่านต่อ |
| `??` | ถ้าค่าซ้ายไม่มี ให้ใช้ค่าขวาแทน |
| `map` | แปลงรายการทุกชิ้นเป็นรูปแบบใหม่ |
| `filter` | เลือกเฉพาะรายการที่ผ่านเงื่อนไข |
| `Promise.all` | เริ่มหลายงานพร้อมกันแล้วรอให้ครบ |
| `db.$transaction` | หลายคำสั่งฐานข้อมูลต้องสำเร็จหรือยกเลิกพร้อมกัน |
| `schema.parse/safeParse` | ตรวจข้อมูลด้วย Zod ก่อนเชื่อถือ |
| `where` | เงื่อนไขเลือกแถวจากฐานข้อมูล |
| `select` | ขอเฉพาะช่องที่จำเป็น |
| `include` | ขอข้อมูลตารางที่สัมพันธ์มาด้วย |

## วิธีอ่าน React / Next.js

- ไฟล์ `page.tsx` คือหน้า URL
- ไฟล์ `layout.tsx` คือกรอบร่วมของหลายหน้า
- ไฟล์ `loading.tsx` และ `error.tsx` คือหน้าสถานะระหว่างรอและเมื่อผิดพลาด
- ฟังก์ชันที่คืน `<section>...</section>` กำลังสร้าง HTML ผ่าน React
- `"use client"` หมายถึงไฟล์นั้นต้องทำงานใน browser เพราะมีการกดปุ่ม state หรือ browser API
- หากไม่มี `"use client"` ให้ถือว่าเป็น Server Component เป็นค่าเริ่มต้นและอาจอ่านข้อมูลฝั่ง server ได้
- `route.ts` ใต้ `src/app/api` คือ API; ชื่อฟังก์ชัน `GET/POST/PATCH/DELETE` ตรงกับ HTTP method

## วิธีอ่านเส้นทางที่มีวงเล็บและวงเล็บเหลี่ยม

- `(public)` ใช้จัดกลุ่มไฟล์ แต่ไม่ปรากฏใน URL
- `[slug]` คือข้อความอ่านง่ายที่เปลี่ยนตามเนื้อหา เช่น `/products/air-model-x`
- `[id]` คือรหัส record ที่เปลี่ยนตามรายการ
- `[kind]` คือประเภทที่ต้องผ่าน allowlist ไม่ใช่ชื่อตารางใดก็ได้

## จุดตรวจความปลอดภัยที่ควรมองหาใน API

1. อ่าน session และตรวจ 2FA/role
2. `assertSameOrigin` หรือ `validMutation` สำหรับคำสั่งเปลี่ยนข้อมูล
3. Zod schema ตรวจ body, params และ query
4. service ตรวจ ownership/permission/business rule
5. transaction เมื่อหลาย record ต้องเปลี่ยนพร้อมกัน
6. audit สำหรับเหตุการณ์สำคัญ
7. generic error และสถานะ HTTP ที่เหมาะสม
8. `Cache-Control: no-store` สำหรับข้อมูลส่วนตัว

ถ้า API เปลี่ยนข้อมูลแต่ขาดข้อใดข้อหนึ่ง ต้องตรวจเหตุผลให้ชัดก่อน merge

## ไฟล์ที่ไม่สามารถใส่คอมเมนต์ได้

ไฟล์ JSON เช่น `package.json`, `package-lock.json` และ `tsconfig.json` ไม่รองรับ comment ตามมาตรฐาน JSON การใส่ comment จะทำให้เครื่องมืออ่านไฟล์ไม่ได้ จึงอธิบายหน้าที่ไว้ที่นี่แทน:

| ไฟล์ | หน้าที่ |
|---|---|
| `package.json` | รายชื่อ dependency และคำสั่ง `npm run ...` |
| `package-lock.json` | ล็อก dependency รุ่นย่อยให้ทุกเครื่องติดตั้งตรงกัน; สร้างอัตโนมัติ |
| `tsconfig.json` | กฎ TypeScript รวมถึง strict mode และ path alias `@/` |
| `next-env.d.ts` | ไฟล์ชนิดข้อมูลที่ Next.js สร้างอัตโนมัติ ไม่ควรแก้ด้วยมือ |

ไฟล์ binary เช่น รูป ฟอนต์ PDF และ generated build output ใส่ comment ไม่ได้และไม่ควรแก้ด้วยมือ ส่วน migration เก่าห้ามเพิ่มแม้แต่ comment เพราะจะเปลี่ยน checksum หลังนำไปใช้ คำอธิบายของ migration จึงต้องอยู่ในเอกสารแยกหรือ migration ใหม่เท่านั้น

## เมื่อแก้โค้ดแล้วต้องตรวจอะไร

```bash
npm run lint
npm run typecheck
npm run test:unit
npm run db:validate
npm run build
```

Integration/E2E ต้องใช้ฐานข้อมูลทดสอบแยกตาม `.env.test.example` ห้ามชี้ไป production รายละเอียดอยู่ใน README และ `docs/DATABASE.md`

## หลักการดูแลคอมเมนต์

- แก้คอมเมนต์พร้อมโค้ดทุกครั้งที่พฤติกรรมเปลี่ยน
- อย่าเขียนความลับ รหัสผ่าน token หรือข้อมูลลูกค้าใน comment
- อย่ารับรองว่าโค้ด “ปลอดภัย 100%” ให้บอกสมมติฐานและข้อจำกัด
- อธิบายว่าทำไมต้องมีกฎ มากกว่าบอกซ้ำว่าโค้ดสะกดอย่างไร
- ถ้า comment กับโค้ดขัดกัน ให้ถือโค้ดและ tests เป็นพฤติกรรมปัจจุบัน แล้วแก้ comment/เอกสารให้ตรงก่อนส่งงาน
