# คู่มือทำความเข้าใจโปรเจกต์ฉบับคนทั่วไป

เอกสารนี้อธิบายว่าเว็บไซต์ของ **บริษัท อยู่เย็นเป็นสุข วิศวกรรม จำกัด** มีส่วนประกอบอะไร ข้อมูลเดินทางอย่างไร และควรเริ่มอ่านโค้ดจากตรงไหน โดยไม่จำเป็นต้องมีพื้นฐานเขียนโปรแกรม

## 1. ระบบนี้ทำอะไร

ระบบมี 2 ส่วนที่ใช้ข้อมูลชุดเดียวกัน

1. **เว็บไซต์สาธารณะ** — ลูกค้าอ่านข้อมูลบริษัท บริการ สินค้า ผลงาน ข่าว และข้อมูลติดต่อได้โดยไม่ต้องล็อกอิน
2. **CMS หลังบ้าน** — Editor และ Super Admin ล็อกอินเพื่อเพิ่ม แก้ไข เผยแพร่ เก็บถาวร ย้ายลงถังขยะ และกู้คืนเนื้อหา

ระบบรุ่นแรกไม่มีบัญชีลูกค้า ตะกร้าสินค้า การชำระเงิน การจองคิว หรือการเก็บข้อความจากแบบฟอร์มติดต่อ

## 2. ภาพรวมการทำงาน

```text
ผู้เยี่ยมชม ──> หน้าเว็บสาธารณะ ──> Service อ่านเฉพาะข้อมูลที่เผยแพร่ ──> PostgreSQL
                                      │
                                      └──> ขอ URL ชั่วคราว ──> S3 เก็บรูป/PDF

ผู้ดูแล ──> หน้า Login ──> รหัสผ่าน + 2FA ──> Session ในฐานข้อมูล
   │
   └──> หน้า CMS ──> API ตรวจ session/origin/ข้อมูล/สิทธิ์ ──> Service ──> Repository ──> PostgreSQL
                                                                  │
                                                                  └──> Audit log
```

คำง่าย ๆ ที่ใช้ในภาพ:

- **API** คือประตูรับคำสั่งจากหน้าจอ เช่น “บันทึกสินค้า”
- **Service** คือส่วนตัดสินกฎธุรกิจ เช่น เผยแพร่ได้หรือไม่
- **Repository** คือส่วนที่คุยกับฐานข้อมูลโดยตรง
- **Session** คือบัตรผ่านชั่วคราวหลังล็อกอิน เก็บใน cookie ที่ JavaScript อ่านไม่ได้
- **Audit log** คือสมุดบันทึกว่าใครทำอะไร เมื่อใด และสำเร็จหรือไม่
- **S3-compatible storage** คือพื้นที่เก็บไฟล์รูปและ PDF แยกจากเครื่องที่รันเว็บไซต์

## 5. ตัวอย่าง: เมื่อ Editor กด “เผยแพร่สินค้า”

1. หน้าจอส่ง `POST` ไปที่ `/api/admin/content/products/{id}/transition` พร้อม `{ "action": "publish" }`
2. API ตรวจว่าคำขอมาจากเว็บไซต์ต้นทางเดียวกัน ลดความเสี่ยง CSRF
3. API อ่าน session จาก cookie และยืนยันว่าบัญชียัง active และผ่าน 2FA แล้ว
4. Zod ตรวจว่า action เป็นค่าที่ระบบอนุญาต
5. Content service ตรวจสถานะเดิมและความสัมพันธ์ของสินค้า
6. Repository เปลี่ยนสถานะเป็น `PUBLISHED` ใน transaction
7. ระบบเขียน AuditLog และล้าง public cache ที่เกี่ยวข้อง
8. เว็บไซต์สาธารณะจึงอ่านสินค้านี้ได้ เมื่อ `publishedAt` ถึงเวลาแล้วและ `deletedAt` ยังว่าง

## 6. สถานะของเนื้อหา

| สถานะ | ความหมาย | เว็บไซต์สาธารณะเห็นหรือไม่ |
|---|---|---|
| `DRAFT` | ฉบับร่าง | ไม่เห็น |
| `PUBLISHED` | เผยแพร่ | เห็นเมื่อถึง `publishedAt` |
| `ARCHIVED` | เก็บถาวร | ไม่เห็น |
| `deletedAt` มีค่า | อยู่ในถังขยะ | ไม่เห็น |

การลบปกติเป็น **soft delete** คือยังไม่ลบแถวทันที ระบบกำหนด `purgeAt` ไว้ 30 วันเพื่อให้กู้คืนได้ การลบถาวรก่อนกำหนดต้องเป็น Super Admin และต้องผ่านกฎความสัมพันธ์ของข้อมูล

## 7. บทบาทผู้ดูแล

- **Editor** จัดการข้อมูลบริษัท banner บริการ สินค้า ผลงาน ข่าว taxonomy และ media ที่อนุญาต แต่จัดการบัญชีผู้ดูแลไม่ได้
- **Super Admin** ทำได้เหมือน Editor และเพิ่ม/แก้/ปิด/รีเซ็ตรหัสผ่าน/รีเซ็ต 2FA ของผู้ดูแลคนอื่น รวมทั้งดู audit history
- ระบบห้ามปิด ลดสิทธิ์ หรือลบ Super Admin ที่ active คนสุดท้าย
- การซ่อนปุ่มในหน้าจอไม่ถือเป็นการรักษาความปลอดภัย ทุกคำสั่งสำคัญตรวจสิทธิ์ซ้ำที่ server

## 8. วิธีเก็บข้อมูลสำคัญ

- รหัสผ่านเก็บเป็น Argon2 hash ไม่เก็บ plaintext
- session cookie เก็บ token แบบ opaque แต่ฐานข้อมูลเก็บเฉพาะ hash ของ token
- TOTP secret เข้ารหัสด้วย key จาก environment และมีเลข version เพื่อรองรับการเปลี่ยน key
- recovery code แสดงครั้งเดียวและเก็บเฉพาะ hash
- รูป/PDF อยู่ใน private S3 bucket; ฐานข้อมูลเก็บ metadata และ object key
- secret จริงต้องอยู่ใน secret manager หรือ `.env` ที่ไม่ commit เท่านั้น
